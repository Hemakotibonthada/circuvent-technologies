## Environments

`VERCEL_ENV` is the source of truth. `src/lib/config.ts` derives:

```ts
DEPLOY_ENV      // "production" | "preview" | "development"
IS_PUBLIC_SITE  // true only for production
```

`NEXT_PUBLIC_DEPLOY_ENV` can override it for a self-hosted or local run.

### Dev is a full pre-production environment

Dev is **not** a crippled copy. It runs the same code with the same features —
real database, working checkout, real flows — on its **own** infrastructure.

| Concern | Production | Dev |
| --- | --- | --- |
| Database | Neon project *Circuvent Shopping* | Neon project *dev.circuvent.com* |
| `ACCOUNT_SECRET`, `JWT_SECRET`, `SESSION_SECRET` | separate values | separate values |
| Payment keys | live | test-mode (to be configured) |
| Email / SMS | live | must not reach real customers |
| `FRONTEND_URL`, `GOOGLE_CALLBACK_URL`, `NEXT_PUBLIC_SITE_URL` | app.circuvent.com (SaaS) / circuvent.com (apex) | dev.circuvent.com |

Only non-sensitive tuning knobs are shared: rate limits, ports, log level,
upload paths, SMTP host/port (useless without credentials).

Dev-specific values are scoped to the **`develop` git branch** in Vercel, so
one-off PR previews do not inherit them.

### Access

An unauthenticated request to `dev.circuvent.com` returns
`401 Protected deployment` — Vercel Authentication gates it, so only signed-in
team members can reach it.

The project setting reads `all_except_custom_domains`, which sounds as though
custom domains are exempt. **They are not**, as an anonymous request shows.
Verify with a real request rather than trusting the setting.

### Only production is indexable

Anything that is not `VERCEL_ENV=production` serves:

- `Disallow: /` from `src/app/robots.ts`
- `X-Robots-Tag: noindex, nofollow` from `next.config.ts`

Both are needed. `robots.txt` alone is not sufficient, because a disallowed URL
can still be indexed without being fetched. Vercel adds the header to
`*.vercel.app` URLs by itself but **not** to a custom domain pointed at a branch,
which is exactly the dev case.

A dev site that Google crawls competes with production for its own search terms
and exposes unreleased work, and it is hard to undo once the URLs are indexed.

Verify after any change to `robots.ts`, `sitemap.ts` or the headers block:

```bash
curl -sI https://circuvent.com/robots.txt     | grep -i x-robots-tag   # expect nothing
curl -s  https://circuvent.com/robots.txt     | head -3                # expect Allow: /
curl -sI https://dev.circuvent.com/robots.txt | grep -i x-robots-tag   # expect noindex
```

## Certificates

- **Vercel** issues and renews certificates for `circuvent.com` and
  `dev.circuvent.com` automatically.
- **Caddy** issues and renews the certificate for `api.circuvent.com`
  automatically, provided ports 80 and 443 stay reachable.
- **Mosquitto** uses Circuvent's **own CA**, generated by
  `platform/scripts/gen-certs.sh` and mounted at `/mosquitto/certs`. Device
  firmware embeds `ca.crt` to trust it.

Mosquitto loads its certificate at start and does not watch the file, so schedule
a weekly reload:

```bash
# crontab -e
0 4 * * 0  cd /home/ubuntu/<repo>/platform && docker compose kill -s HUP mosquitto
```

## Adding a new environment

To add, say, `staging.circuvent.com`:

1. Create a `staging` branch.
2. Add the domain in Vercel and bind it to that branch.
3. Add a CNAME at GoDaddy pointing to the Vercel target.
4. Give it its **own** database and its own secrets — never reuse production's.
5. Add its database host to `PROD_DATA_HOSTS`? **No.** That list names hosts only
   production may use. Staging needs its own host *absent* from that list.
6. Scope `NEXT_PUBLIC_SITE_URL`, `FRONTEND_URL` and `GOOGLE_CALLBACK_URL` to the
   new branch.

It will be `VERCEL_ENV=preview`, so it is automatically non-indexable.
